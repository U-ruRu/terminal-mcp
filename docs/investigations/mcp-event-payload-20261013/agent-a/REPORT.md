# MCP Events: отсутствие payload у dot — источники и независимая проверка

Дата исследования: 13 октября 2026 года, Asia/Tbilisi (12 октября UTC).
Исполнитель A: Papa-5. Исполнитель B: Quebec-5 / Uniform-156. Координатор dot: Romeo-5.
База проверки кода: `4ecb7201bcc8e2d7ce2b75fcb18d2f77690a66e4`.
Ветка A: `docs/mcp-events-payload-sources-papa5-20261013`.

## Вывод

Публичный официальный пример отправителя, заявленный применимым к dots, существует [O].
Найдено также совпадающее публичное сообщение об ошибке: одинаковые события видны в Work,
а у dot отсутствует обещанный результат `automations.mcp_event` [I]. Автор сообщает о воспроизведении
в другой реализации; мы его живой эксперимент не повторяли. Причину нашего инцидента
это сообщение не устанавливает.

Прочитанные отправители используют один и тот же внешний формат. Проверка нашей функции
подписи по опубликованному контрольному примеру Standard Webhooks прошла. Оснований
добавлять другую JSON-обёртку или менять имя поля наугад не найдено.

Самостоятельного подтверждения успешной передачи полного webhook payload именно в
контекст dot без дополнительных чтений среди проверенных материалов не получено.
Документированный контракт доставки существует; внутренний контракт вставки
`automations.mcp_event` в контекст публично не найден. Точный внутренний этап потери данных
остаётся неизвестным. До сопоставления нового события с непосредственным наблюдением dot
критерий задачи не выполнен.

## Внешний контракт

[O] прямо относит механизм к Work и dots, требует MCP `2026-07-28`, приводит Node.js
`sendEvent` и отличает подтверждение HTTP от последующей обработки. HTTP Last-Modified
проверенной Markdown-страницы: `2026-10-12T20:38:58Z`; это метаданные ответа, не дата
первой публикации. SHA256 страницы сохранён в `sources.json`.

Ниже единый профиль из draft [D], библиотеки подписи [S] и прочитанных реализаций [R, H, F, P].
Значения в угловых скобках обозначают поля схемы, не действующие реквизиты.

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "events/subscribe",
  "params": {
    "name": "<event-name>",
    "arguments": {"<declared-filter>": "<value>"},
    "delivery": {
      "mode": "webhook",
      "url": "<platform-provided-HTTPS-callback>",
      "secret": "<platform-provided-secret>"
    },
    "cursor": null
  }
}
```

Ответ подписки содержит `id`, `refreshBefore`, `cursor`, `truncated`. Проверка callback
использует отдельное подписанное тело `{"type":"verification","challenge":"..."}`.
Прикладное событие передаётся самостоятельным объектом:

```json
{
  "eventId": "<stable-event-id>",
  "name": "<subscribed-event-name>",
  "timestamp": "<RFC3339-event-time>",
  "data": {"<payloadSchema-field>": "<value>"},
  "cursor": null
}
```

HTTP-метод `POST`. Заголовки: `Content-Type: application/json`, `webhook-id: <eventId>`,
`webhook-timestamp: <Unix-seconds>`, `webhook-signature: v1,<base64-HMAC>` и
`X-MCP-Subscription-Id: <subscription-result-id>`. Имена заголовков регистронезависимы.
Ключ подписи — base64-декодированная часть секрета после `whsec_`; сообщение HMAC-SHA256 —
конкатенация `webhook-id`, точки, timestamp, точки и точных сериализованных байтов тела.
Подписывается именно отправленное тело. Другие служебные JSON-обёртки в проверенных
отправителях отсутствуют.

В профиле ChatGPT ограничение полного тела — 256 KiB. Один POST содержит одно событие;
пакетный запуск ChatGPT объединяет отдельные доставки. Само пакетное уведомление не
устанавливает число полученных событий. Повтор доставки сохраняет eventId, обновляя
время подписи. HTTP 2xx подтверждает приём, а видимость полей требует отдельной проверки [O].

## Механизмы, которые не доказывают совместимость

OpenAI API webhooks — обратное направление: OpenAI уведомляет приложение, например
о `response.completed`; другая структура полей и назначение.
Источник: https://developers.openai.com/api/docs/guides/webhooks

Streamable HTTP/SSE переносит JSON-RPC ответы и уведомления MCP-клиенту через
соединение транспорта. Это не самостоятельный подписанный callback MCP Events,
создающий запуск dot. Источник транспорта версии 2025-11-25:
https://modelcontextprotocol.io/specification/2025-11-25/basic/transports

Пользовательский `cloud_threads.notifications` также не заменяет доказательство
по `mcp_server/event`. Доступность поля в обычном результате инструмента или
после inbox/read не устанавливает наличие первоначального webhook payload.

## Локальная работа и оставшиеся доказательства

A работал в отдельном worktree через собственную Legacy-сессию Secondary. Access-B
и создание автоматизаций отсутствуют в доступном A каталоге; live-часть закреплена
за B, у которого есть собственная BacLOUD Access-сессия. Чужие коды сессий и
подписки не использовались. Продуктовые изменения, очистки и перезапуски не выполнялись.

Нужен единый контроль: B сохраняет фактически отправленные байты и обезличенные
метаданные, dot независимо выписывает полученные поля, затем eventId и содержание
сравниваются. Значения nonce не передаются dot заранее через координацию.
Статус и точный протокол находятся в `LIVE-CONTROL.md`; сведения из B требуют
cross-review, а не автоматического признания.

Если подтверждённый запрос соответствует профилю, автоматизация запускается,
а promised tool result по-прежнему отсутствует, пакет предназначен платформе:
точная потеря находится в недоступной проверке приёма/сохранения/вставки контекста.
Без платформенных журналов эти внутренние этапы друг от друга неотличимы.
Полноценное решение подтверждает только новый совпадающий payload у dot.
