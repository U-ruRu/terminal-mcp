# MCP Events: сравнение с публичными реализациями и HTTPS-контроль

Дата: 13 октября 2026 года, UTC. Участки A и B выполнялись разными исследователями.
Координатор: dot. Отправная точка: `b6b0605d893444ccce50089c6a865891fb63d8f8`.
Изменения изолированы в отдельной исследовательской ветке.

## Вывод

На трёх синтетических событиях настоящий локальный HTTPS-приёмник получил **побайтно
одинаковые тела** от нашего Python-адаптера и официальной функции OpenAI `sendEvent`.
Совпали значения пяти обязательных заголовков и `Content-Length`, включая подпись.
Публичные функции подписания Hookdeck и Recly также дали ту же подпись для каждого тела.
Это существенно сильнее прежнего сравнения схем и теста с подставным sender.

Различие транспорта в этой фикстуре: Python прислал `Accept-Encoding: identity`, Node —
`Connection: close`. Имя/регистр заголовков нормализованы при сравнении; утверждения о
полном совпадении всех HTTP-заголовков или TLS-пакетов нет. Причинной связи этих двух
транспортных различий с отсутствием tool-result у dot не установлено.

Критерий фактической видимости payload у dot остаётся открытым. Производственный формат
не менялся. Ключи/URL рабочих callbacks не получались, тестовые события в production из A
не отправлялись, серверы не перезапускались. Изолированный приёмник остановлен после проверки.

## Что проверено на сервере

`git ls-remote` подтвердил текущую опубликованную базу. `git diff 4ecb7201..b6b0605d --
src/terminal_mcp/mcp/event*` пуст: проверявшийся отправитель не изменился при последующем
исправлении идентичности. Версии из старого PROJECT_CONTEXT.md не использованы как runtime-факт.
Текущее состояние рабочего сервера проверяет B; совпадение отправителя отдельно сохранено SHA256:
`43720d32a3bbb3059c8668f727efa30130dd000ae30f31511fb90e19d2db3659`.

## Дополнение: проверенный поставщиком сценарий Upstash

Поставщик прямо [пишет о сквозной проверке с ChatGPT monitors](https://upstash.com/docs/redis/sdks/agentkit/mcp-events#example).
[Публикация от 9 октября](https://upstash.com/blog/mcp-tasks-and-events) конкретизирует клиент как Work.
Это полезный рабочий образец по заявлению автора; его облачную установку мы не воспроизводили.

В исходниках и документации обнаружено реальное правило этой библиотеки: все фильтры `input`
должны присутствовать в `payload`, и matching сравнивает их значения. У Terminal MCP
`session_number` служит при подписке для разрешения и закрепления допустимого адресата,
а `data` содержит публичное имя адресата и само сообщение. Это разные модели серверной
маршрутизации. Официальный контракт описывает `inputSchema` и `payloadSchema` отдельно и
не устанавливает общее требование копировать каждый параметр подписки в `data`.
Проверка Upstash не оправдывает раскрытие нашего номера доступа в webhook payload.

Другие найденные отличия: QStash вызывает серверный handler, тот подписывает событие
секретом получателя; это два разных этапа с разными подписями. Подпись QStash не передаётся
как замена Standard Webhooks. Upstash документирует отсутствие DNS-проверки в своей
проверке callback и требует egress filtering. Наш runtime проверяет адреса и закрепляет
соединение. Это эксплуатационные/защитные отличия, не обнаруженное средство исправления
отсутствующего tool-result. Их live-поведение не экстраполируется из локальной фикстуры.

## Взаимная проверка

Второй исследователь независимо повторил шесть локальных TLS-запросов и четыре отрицательные
проверки CLI. Затем A прочитал его полный отчёт и JSON-квитанции, пересчитал SHA256 всех тел
и проверил соответствие eventId/header и шесть полей данных. `peer-review.json` фиксирует
снимки и границы: выполнена независимая offline-проверка; новая видимость payload в Work/dot
в этом материале не подтверждена.

## HTTPS-эксперимент

`https_fixture.py` запускает короткоживущий TLS-приёмник только на loopback и вызывает
неизменённые `MCPEventsAdapter.deliver_due → post_signed → _pinned_https_post`.
Хранилище и проверка области доступа синтетические. Test-only DNS/IP/socket facade отображает
один RFC 5737 адрес в этот конкретный listener и имитирует его admission как публичного.
Это не проверка настоящего DNS или production IP-классификации. TLS проверяет цепочку и hostname
по временному сертификату. Production URL, секреты, БД и политики не используются.

Официальная функция извлекается из закреплённого по SHA256 документа без изменения её тела.
`Webhook` — настоящий `standardwebhooks@1.1.1`; зависимые `fast-sha256@1.3.0` и
`@stablelib/base64@1.0.1` закреплены lockfile. Hookdeck signer исполняется с удалённой только
TypeScript-сигнатурой функции; Recly — три отдельно просмотренные функции, без запуска его сервера.

Три случая: одиночный ASCII; Unicode/кавычки/перенос/emoji; второй элемент пары.
Наш adapter обрабатывает сначала singleton, затем две due-записи: это два отдельных POST.
Node отправляет те же три event objects. Итого шесть реальных локальных HTTP-запросов через TLS.

`https-fixture-result.json` содержит тела, размеры, SHA256, заголовки с убранной подписью,
результат проверки HMAC и ответы локального приёмника. **Его HTTP 200 — синтетический ответ,
не ответ ChatGPT.** В JSON прямо записано `live_model_visibility_proven:false`.

## Дополнительная диагностическая утилита

`reference_sender.mjs` подготовлен для потенциального согласованного one-shot опыта, но
**в этом запуске его live-использование не разрешено координатором и не выполнялось**.
Перенос callback-секретов на сервер разработки исключён. Утилита не меняет подписки и не повторяет POST.
Она проверяет публичность всех DNS-адресов, закрепляет соединение, сохраняет TLS hostname check,
не следует redirects, ограничивает тело и ответ. Ввод credentials возможен только через stdin.

По независимому review B учтены границы записи receipt: файл резервируется до сети,
фиксируются фазы, различаются `not_attempted` и неопределённый результат доставки.
Ошибка не печатает произвольный exception text. Короткие проверки отказа для занятого capture
и private callback прошли до HTTP; проверки redaction сохранены в `reference-safety-result.json`.
Это качество диагностической утилиты, а не исправление исходного дефекта Terminal MCP.

## Наблюдения принимающей стороны

Координатор сообщил, что поздние одиночный и пакетный контрольные запуски предыдущего дня
прошли с отсутствующим payload. Старый отчёт был подготовлен раньше этих запусков, поэтому
его статус «контроль ещё не выполнен» не описывает поздний результат. Точные операционные
идентификаторы и сообщения сохранены отдельно в ignored `.local-ops/`, вне публичного отчёта.

По просьбе оператора создан отдельный чат получателя. Его первоначальная среда оказалась
Codex: нет создания MCP Events подписки и маршрута payload в этот чат. Сессия и события
не создавались. Это **capability_blocked**, а не failed webhook и не payload_absent.
Координатор организует проверку именно Work; фактический результат фиксируется отдельно.
В этом отчёте новая видимость payload не объявляется подтверждённой.

В старой переписке есть текстовое свидетельство получателя о реально видимых полях
`session.ended` в Work. Сырой tool-result не извлечён. Этот материал отделён от новой
приёмки и от непосредственного capture; точные операционные значения остаются вне Git.

## Воспроизведение

Из корня worktree, с Node 22, OpenSSL и активированной test-venv проекта:

```sh
D=docs/investigations/mcp-event-payload-20261013/agent-a-followup
python3 "$D/prepare_sources.py" --output /tmp/tmcp-events-reviewed-sources
PYTHONPATH=src python "$D/https_fixture.py" \
  --sources /tmp/tmcp-events-reviewed-sources --output /tmp/tmcp-events-https-result.json
```

Подготовка проверяет SHA256 трёх входных файлов, npm использует lockfile и `--ignore-scripts`.
Полная приёмка и сторонние серверы не запускаются. Проверяемая граница — сериализатор,
подпись и доставка bytes на локальный TLS-приёмник. Для завершения задачи всё ещё нужна
прямая видимость одного согласованного события в нужном клиенте и сравнение eventId/data
до любых восстановительных чтений.
