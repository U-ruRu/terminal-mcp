## Blocking findings, each with executable counterexamples

**B1 — Lost action-specific required field (`coordinator.task_manage update`).**
- Source: `application/task_requests.py:198-201`, `TaskUpdateRequest.expected_revision: ExpectedRevision` is required, non-null. Handler dispatch: `mcp/roles.py:894-899`.
- Generated: `catalog-coordinator.json -> tools[task_manage].inputSchema.allOf` requires only `task_id` when `action=update`; textual `Conditions` does not name `expected_revision` as required. `Arguments` calls it optional and `Runtime rules` merely says canonical variants enforce fields.
- **Counterexample:** `{"action":"update","namespace":"qa","task_id":"t","title":"x"}`. Published JSON Schema VALID; top-level TaskManageInput VALID; canonical TaskUpdateRequest fails `missing expected_revision` and isolated MCP returned structured `input_validation_failed` with `path=expected_revision`.
- Also `"expected_revision":null` is accepted by public top-level schema but invalid for update.

**B2 — Nine incomplete action-specific allowed-field lists (`coordinator.task_manage`).** `TaskManageInput` exposes a union of 33 keys with `additionalProperties:false`; its action conditions do **not** restrict the allowed subset for each action. Each canonical model has `extra="forbid"`; the generated description never enumerates action-specific whitelists. Independently verified examples (each passes future public JSON Schema and top-level model, fails canonical `extra_forbidden`):

| Action | Add forbidden field to canonical-valid action payload | Strict source |
|---|---|---|
| create | `{"action":"create","namespace":"qa","isolation_hint":"isolated","archive_note":"x"}` | `TaskCreateRequest` |
| update | `{"action":"update","namespace":"qa","task_id":"t","expected_revision":1,"checkpoint":"x"}` | `TaskUpdateRequest` |
| checkpoint | `{"action":"checkpoint","namespace":"qa","task_id":"t","checkpoint":"x","title":"x"}` | `TaskCheckpointRequest` |
| archive | `{"action":"archive","namespace":"qa","task_id":"t","note":"reason","title":"x"}` | `TaskArchiveRequest` |
| review | `{"action":"review","namespace":"qa","task_id":"t","dimensions":["A"],"verdict":"NON_BLOCKING","title":"x"}` | `TaskReviewRequest` |
| relate | `{"action":"relate","namespace":"qa","task_id":"t","relation_kind":"blocks","related_task_id":"u","title":"x"}` | `TaskRelateRequest` |
| unrelate | `{"action":"unrelate","namespace":"qa","task_id":"t","relation_kind":"blocks","related_task_id":"u","title":"x"}` | `TaskUnrelateRequest` |
| state | `{"action":"state","namespace":"qa","task_id":"t","state":"qa","title":"x"}` | `TaskStateRequest` |

**B3 — Incorrect absolute requirement for archive.** First sentence of `coordinator.task_manage` description says `archive needs archive_note`; later conditions correctly allow `archive_note OR note`. Source `TaskArchiveRequest` (`application/task_requests.py:265-290`) and `core/tasks.py:1525-1533` accept `{"action":"archive","namespace":"qa","task_id":"t","note":"reason"}` without archive_note. Correct the contradictory prefix.

**B4 — Invented conditional release_reason requirement.** `executor.task_claim` runtime annotation says `release_reason may be required when an existing live claim is released`; source `TaskReleaseRequest.release_reason` is optional (`application/task_requests.py:187-194`) and `core/tasks.py:1299-1303` explicitly substitutes `released_by_owner`. Valid `{"action":"release","namespace":"qa","task_id":"t"}`; no runtime check makes the field required.

**B5 — Obsolete ownership restriction in task_state.** `executor.task_state` describes modifying `a task owned by the current LogicalAgent`; `core/tasks.py:1486-1510` and `storage/tasks.py:884-886` allow **any admitted agent** to set a valid state regardless of existing claims, archives, dependencies, result or content revision. A different attached agent may send `{"namespace":"qa","task_id":"t","state":"qa"}` for another agent's claimed task. That request is valid; actual state mutation still depends on task existence and admission.

**B6 — `task_claim` action/null and extra-field omissions.** Source `TaskClaimRequest.claim_intent` is a non-null required string (`application/task_requests.py:180-184`) and `TaskReleaseRequest` does not allow `claim_intent`; `TaskClaimRequest` does not allow `release_reason`. Generated role schema says required presence only and allows nullable intent and cross-action extras. Counterexamples:
- `{"action":"claim","namespace":"qa","task_id":"t","claim_intent":null}` — public VALID, canonical invalid null.
- `{"action":"claim","namespace":"qa","task_id":"t","claim_intent":"x","release_reason":"y"}` — public VALID, canonical extra_forbidden.
- `{"action":"release","namespace":"qa","task_id":"t","claim_intent":"x"}` — public VALID, canonical extra_forbidden.
All were reproduced with direct source-model differential checks.

**B7 — `message` forbidden-field semantics are over-absolute (both roles).** `role_contracts.py:173-194` tests `is not None`, not key presence. The generated runtime description says `send forbids message_hash`, `ack forbids text`, `read/history/recipients forbid text and message_hash`. In reality `{"action":"send","text":"ok","message_hash":null}`, `{"action":"ack","message_hash":"h","text":null}` and `{"action":"read","text":null}` are accepted by Pydantic (None is dropped before downstream execution). Say **non-null value forbidden**; this is an exact null-vs-omitted semantic distinction. A `send` with `"text":null` is rejected after model validation, although JSON Schema conditional merely checks field presence.

**B8 — `executor.task_comment` operation-specific extra/null limits under-described.** Canonical `TaskCommentRequest` requires non-null `comment_text`; `TaskCheckpointRequest` requires non-null `checkpoint`. Their mutual *extra-forbid* is checked by `MeshTaskCommentInput.to_request()`, not the public schema (`mcp/access_contracts.py:44-80`). All pass generated JSON Schema but fail server input:
- `{"namespace":"qa","task_id":"t","comment_text":null}`.
- `{"namespace":"qa","task_id":"t","comment_text":"ok","checkpoint":"other"}`.
- `{"action":"checkpoint","namespace":"qa","task_id":"t","checkpoint":"ok","comment_text":"other"}`.
Description says action selects canonical model, but omits these actual forbidden combinations.

**B9 — Null-vs-presence gaps for `task_manage` action requirements.** The generated top-level `allOf/if/then` checks field presence, but canonical models require a non-null *value*. Each example passes public schema and top-level `TaskManageInput` but fails canonical:
- `{"action":"checkpoint","namespace":"qa","task_id":"t","checkpoint":null}`.
- `{"action":"state","namespace":"qa","task_id":"t","state":null}`.
- `{"action":"review","namespace":"qa","task_id":"t","dimensions":null,"verdict":"NON_BLOCKING"}`.
- `{"action":"review","namespace":"qa","task_id":"t","dimensions":["A"],"verdict":null}`.
- `{"action":"archive","namespace":"qa","task_id":"t","archive_note":null,"note":null}`; canonical demands at least one non-null.
- `{"action":"create","namespace":"qa","isolation_hint":"isolated","state":"done","result":null}`; source `TaskCreateRequest.require_result_for_done` disallows it, correctly mentioned in runtime annotation.
Descriptions must state exact conditional non-null requirements for all actions, not just done/archive.

**B10 — Unexplained update/replace/null semantics.** Handler `roles.py:894-899` uses `model_dump(exclude_none=True,exclude_unset=True)`; `application/task_requests.py:341-347` also drops None; `core/tasks.py:1560-1606` builds changed fields only from non-null values. Thus for `update`, `description:null` is treated as **omitted/no change**, while `tags:[]` is an explicit empty-array replacement. The generated `task_manage` description does not say whether null clears or omits, nor whether arrays replace rather than append. Minimal diagnostic requests: `{"action":"update","namespace":"qa","task_id":"t","expected_revision":1,"description":null}` and the same with `"tags":[]`. The difference affects client mutation planning.

**B11 — Public pre-server rejection/schema dump risk (release blocking).** All 19 proposed input schemas have `additionalProperties:false`; they also carry required/enum/conditional/type/bound/ref assertions. Example: `executor.command_run {"command":42}` is rejected by the **future** published schema before reaching server if the client enforces it. In the actual currently published permissive schema, isolated HTTP MCP transmits this input to the server and gets a compact structured error. Python `jsonschema` prevalidation for `coordinator.task_manage {"namespace":"qa"}` produced an **18,382-byte exception string** for a 6,501-byte compact input schema; this is a *Python-validator demonstration*, **NOT** measured ChatGPT behavior. The exact client engine, schema-dump formatting and token exposure remain **NOT TESTED**. The release gate must independently prove that errors in ChatGPT do not echo the entire schema; consider permissive transport schema plus precise description if necessary.

**B12 — Description explicitly advertises a forbidden checkpoint parameter.** `executor.task_comment` generated description starts with `checkpoint ... optional expected_revision` inherited from `mcp/roles.py:979-987`. The actual `MeshTaskCommentInput` (`mcp/access_contracts.py:44-80`) has *no* `expected_revision` property and uses `extra="forbid"`. The future `inputSchema` also rejects it. Minimal `{"action":"checkpoint","namespace":"qa","task_id":"t","checkpoint":"ok","expected_revision":1}`: misleading prose **claims optional field**, generated JSON Schema **rejects extra**, strict Pydantic **rejects extra**. Correct the stale source description before publishing. Distinguish the **current candidate d1caea24** from prior live bde0.

**B13 — Relation special-kind runtime rule omitted; do not invent relation_kind enum.** `coordinator.task_manage` source `TaskRelateRequest.relation_kind` (`application/task_requests.py:230-241`) accepts any string with 1–64 chars, NOT a fixed enum; `{"action":"relate","namespace":"qa","task_id":"t","relation_kind":"qa_arbitrary_rel","related_task_id":"u"}` is valid in canonical input and public JSON Schema. However the special value `relation_kind="review_of"` triggers additional runtime constraints at `storage/tasks.py:2003-2065`: source task must have `lane="review"`, parent must have nonempty `candidate_ref`, no conflicting second `review_of` parent and source candidate must match parent candidate. Generated description says simply `relate/unrelate need relation_kind/related_task_id`, with no mention of conditional `review_of` constraints. Minimal runtime failure example: `{"action":"relate","namespace":"qa","task_id":"nonreview_task","relation_kind":"review_of","related_task_id":"parent_with_candidate"}` on existing non-review source and populated parent; schema/canonical accepts but storage returns `review_task_required`. Must describe conditional rules while keeping `relation_kind` open-ended.
