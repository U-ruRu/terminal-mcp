# Terminal MCP: целевой продуктовый контракт Mesh и агентских сессий

> **Статус:** нормативная целевая архитектура (to be implemented). Этот документ определяет требуемое поведение продукта; наличие описанного здесь поведения в текущем релизе не подразумевается. При противоречии с документацией существующей реализации для новой разработки приоритет имеет настоящий контракт.

## 1. Основные понятия и неизменные правила

- **Узел** — самостоятельно установленный сервер Terminal MCP с Access (ACS), Execution и Coordination.
- **Standalone** — узел без членства в Mesh. Это топологическое состояние, а не отдельный runtime, протокол или модель авторизации. Standalone не объявляется автоматически отдельным Mesh.
- **Mesh** — назначенное пользовательским приложением объединение одного или нескольких узлов. Mesh может содержать единственный узел.
- **Основной узел Mesh** — единственный авторитетный источник общего реестра слотов и политики данного Mesh. Другие узлы предоставляют равноправные точки входа и используют согласованное состояние Mesh.
- **Pairing** — подтверждённая связь пользовательского приложения с узлом, предоставляющая приложению полномочие управлять его топологией.
- **Слот** — запись общего пространства регистрации агентов соответствующего Mesh; в Standalone слот принадлежит локальному пространству автономного узла.
- **Рабочая сессия** — локальное выполнение агентом работы на выбранном узле с авторизацией по слоту текущего пространства.

Продукт использует один термин **Mesh** для объединения серверов. Подключение, отделение и перенос узла являются изменениями топологии, а не сменой режима агентов. Один и тот же узел всегда предоставляет один и тот же интерфейс инструментов и одну модель проверки доступа.

## 2. Единый агентский контракт

Каждый узел всегда предоставляет одинаковые публичные MCP-роли, инструменты и семантику:

| Роль | Сессия / назначение |
| --- | --- |
| Access (ACS) | Выдача номера слота через `session(action="start")`, завершение цикла через `session(action="end")`, события доступа. |
| Execution | `session(action="attach", session_number=...)`, `session(action="intent", intent=...)`, выполнение и чтение команд, задачи и сообщения. |
| Coordination | Такие же `attach` и `intent`, управление задачами, наблюдение и сообщения. |

Для всех топологий обязательны одни и те же имена инструментов, аргументы, опубликованные универсальные объектные схемы, подробные описания, строгая серверная валидация, структура ошибок и правила авторизации. Набор инструментов не зависит от Standalone, количества узлов Mesh или роли конкретного узла как основного.

Исполнение старой ролевой модели `session(start/end/interrupt)`, альтернативные MCP-каталоги, старые валидаторы и переключатели совместимости **удаляются**. Действующие `start/end` относятся только к Access; Execution и Coordination используют только `attach/intent`.

Каждая рабочая сессия исполняется на конкретном узле, но регистрация агента и доступность слота определяются текущим пространством Mesh. Локальные очереди, процессы и результаты команд остаются локальными ресурсами узла.

## 3. ACS и общее пространство слотов

1. **ACS работает внутри текущего Mesh, а не в изолированном реестре конкретного узла.** Через Access Connector любого участника можно зарегистрировать агента в общем Mesh и использовать его слот на любом действующем участнике этого Mesh.
2. Основной узел обеспечивает авторитетный реестр слотов и политики. Остальные узлы обращаются к нему и/или поддерживают согласованные данные, достаточные для проверенного `attach` и работы при предусмотренных отказах связи. Выдача и завершение не создают независимых несовместимых реестров на отдельных узлах.
3. У Standalone нет удалённых участников: собственный Access, локальный реестр и те же правила `start/end/attach/intent` работают самостоятельно.
4. При переходе Standalone в Mesh прежние слоты автономного пространства **не переносятся** в новый Mesh. После смены членства узел использует общее пространство назначения.
5. Слоты, идентичности агентов, привязки, полномочия и сообщения одного Mesh не становятся ресурсами другого Mesh из-за pairing или переноса узла. Standalone аналогично изолирован от остальных пространств.
6. Участники одного Mesh принимают один и тот же действительный слот независимо от того, на каком из их Access Connector он был выдан. Привязка к конкретному Connector не ограничивает доступ другими узлами того же Mesh.

Пример: у Mesh X основной узел A и участники B, C. Агент получает номер через ACS сервера B, затем выполняет `attach` к Execution C и Coordination A. Использовать ACS основного узла A для этого не требуется.

## 4. Управление топологией и доверие

**Единственный источник решений о составе Mesh — пользовательское приложение.** После pairing пользователь через приложение вправе:

- оставить узел автономным, создать Mesh из одного узла или добавить новые узлы;
- назначить и заменить основной узел;
- присоединить Standalone к существующему Mesh;
- отделить узел от Mesh в Standalone;
- переместить узел из одного Mesh в другой.

Сам сервер не вводит собственных продуктовых запретов на присоединение из-за текущего имени пространства, прежнего основного узла, списка ручных разрешений или необходимости получать согласие прежнего Mesh. Перевод между Mesh не требует предварительного превращения узла в «специальный режим» и не зависит от того, в каком пространстве он работал ранее.

Сервер **обязан** проверять криптографическую подлинность и действующую pairing-авторизацию управляющего приложения, согласованность операции и условие отсутствия активной работы. Это проверка полномочий пользователя и безопасности исполнения, а не отдельное право сервера отвергнуть выбранную приложением топологию.

После подтверждённого приложением назначения Mesh доверие между действующими участниками и необходимые транспортные полномочия настраиваются автоматически. Peer-подключения не требуют ручного одобрения каждого сервера. На отделённом узле немедленно прекращается доверие, полученное исключительно из прежнего членства. Pairing с приложением и самостоятельная идентичность узла сохраняются.

## 5. Join, Detach и перенос: границы слотов

Изменение членства выполняется только при отсутствии активных слотов и работающих агентов в затрагиваемой области операции. Незавершённая локальная работа должна быть безопасно завершена до перехода. При нарушении условия операция не применяется, а приложение получает конкретную причину блокировки. Это единственный обязательный продуктовый запрет на перенос помимо проверки pairing и корректности самой операции.

Изменение членства атомарно с точки зрения допуска новых `attach` либо восстанавливается идемпотентно после сбоя. Узел не должен временно принимать слоты обоих пространств.

### Перемещение C из Mesh X в Mesh Y

Исходно Mesh X содержит узлы A, B, C и общий набор слотов X. Mesh Y содержит D и общий набор слотов Y. Пользователь через приложение перемещает C в Y:

1. Приложение подтверждает pairing и отсутствие активных слотов / работы в затронутых областях; затем изменяет членство C.
2. **Только на C** удаляются локальные записи слотов прежнего пространства X, их реплики, привязки и старые полномочия Mesh. Слоты C не мигрируют в Y.
3. **У Mesh X сохраняется весь общий набор слотов X без изменений**, включая слоты, которые когда-то были выданы через Access Connector C. Основной узел X ничего не отзывает и не удаляет в своём реестре слотов из-за ухода C.
4. A и B продолжают принимать слоты X. На C `attach` со слотом X после переноса отклоняется, а действительными становятся только слоты Y.
5. D и C используют единый реестр слотов Y. Никакие записи X не переносятся в Y.

При **Detach C в Standalone** действует та же очистка локальных данных X. C начинает собственное пустое пространство слотов и сохраняет прежний агентский интерфейс. Слоты X остаются действительными на остальных участниках X.

Если перемещается **основной узел**, а в исходном Mesh остаются участники, приложение назначает нового основного и до очистки уходящего узла обеспечивает сохранение всего общего реестра слотов исходного Mesh. Изменение основного не отменяет ни один его слот. Если в исходном Mesh больше не остаётся узлов, обязанность сохранять несуществующее пространство Mesh отсутствует.

При изменении членства могут обновляться топологические записи и доверенные peer-связи, но это **не является изменением слотов** оставшегося Mesh. От старого основного узла не требуется отзыв регистраций или очистка слотов.

## 6. Политика слотов

- У каждого Mesh есть общая наследуемая политика слотов, управляемая через приложение и обслуживаемая основным узлом.
- Для конкретного слота можно назначить индивидуальную политику/переопределение.
- Standalone применяет такую же модель политики на своём локальном узле.
- При присоединении узел использует политику нового Mesh. Изменение наследуемых значений при смене членства допустимо; смена модели агентских инструментов недопустима.
- Изменение политики отдельного слота — самостоятельная операция, не скрытый побочный эффект переноса сервера.

## 7. Развёртывания и отказ от старой системы

**Чистая установка / явно выбранный clean deploy:**

- Все ранее сохранённые данные, регистрации, слоты, привязки, pairing, настройки членства и локальные секреты прежней установки сбрасываются. Локальные резервные копии прежней инсталляции удаляются в рамках явно выбранного clean deploy; автоматического восстановления из резервных копий нет.
- Узел запускается Standalone с единственной современной системой Access, Execution и Coordination, готов к новому pairing и назначению Mesh.
- Наличие прежних баз, установочных артефактов или сохранённой топологии не превращает clean deploy в горячее обновление.

**Горячее обновление / upgrade существующей установки:**

- После обновления работает та же единственная современная система. **Старый runtime и протоколы работы агентов не поддерживаются ни на чистых установках, ни при горячем обновлении.**
- Требуемые постоянные данные действующей установки переводятся однократной миграцией; прежние режимы, переключатели и отдельные каталоги не остаются исполняемыми fallback-путями.
- Обновление сохраняет согласованное действующее состояние установки; при невозможности безопасной миграции активация нового релиза не должна создавать частично работоспособную инсталляцию. Очистка всех данных допускается только для явно выбранного clean deploy.
- После активации обновления пользовательское приложение управляет Mesh по тем же правилам, что и после чистой установки.

## 8. Критерии приёмки целевой архитектуры

1. Списки инструментов, схемы, документация, валидные вызовы и ошибки Access/Execution/Coordination совпадают для Standalone, Mesh из одного узла и Mesh из нескольких узлов.
2. Новый сервер без peer-подключений поддерживает Access → `start` → `attach` → `intent` → локальную работу. Pairing позволяет сразу создать Mesh или присоединить узел к существующему.
3. Слот, выданный через Access любого участника X, действителен на всех узлах X и недействителен в независимом Mesh Y.
4. Приложение может авторизованно выполнять Join/Detach/Move независимо от истории членства узла. Сервер не требует дополнительных ручных доверительных разрешений между узлами.
5. При наличии активных слотов или работы в затронутой области перенос запрещается до завершения работы.
6. После переноса C из X в Y слоты X остаются **без изменений** на A и B, включая выданные через C; C удаляет только свои локальные данные X, отвергает старые слоты X и принимает слоты Y.
7. При выходе основного узла оставшийся Mesh сохраняет общий реестр слотов у нового основного.
8. Данные агентов и слотов разных Mesh и автономных узлов не смешиваются; устаревшее доверие и привязки не переживают смену членства.
9. Наследование политики Mesh и индивидуальные переопределения слота работают одинаково при любом количестве участников.
10. Clean deploy оставляет чистый Standalone, upgrade сохраняет согласованные актуальные данные. Ни одна установка и ни одно обновление не предоставляют старые ролевые операции `start/end/interrupt` или альтернативную legacy-схему.
